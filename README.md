## Product brief

Scout should collect relevant events and official announcements into one maintained record, then help users answer questions such as:

> @scout does HSA have any webinars coming soon?

The planned experience includes:

- Updates on treaty ratifications and other official participant-status changes.
- BBNJ webinars, conferences, side events, and official DOALOS announcements.
- Focused Slack announcements when highly relevant findings are discovered, plus an optional weekly roundup of important upcoming events.
- Slack answers grounded in collected records, with supporting source links and visible coverage limits.
- A searchable, filterable web list with supported UTC event times and source links.
- A frontend list of all trackers showing collection status and last successful collection, including trackers that have never succeeded or are overdue.

The Letter mentions an optional weekly email digest; the confirmed POC uses a weekly Slack digest. Outbound email and a separate calendar view remain deferred; calendar generation/actions and native import are out of scope. See SCOUT-01 in tasks.md for the recorded scope decision.

## Records and collection

Records keep a title, type, organization, description of at most 280 characters, location, event/registration links, supported UTC start/end timestamps and status. Publication and collection timestamps belong to sources. Full text, date-only values and treaty details remain in captured source evidence; records no longer duplicate them in summary, date-only, publication, country, treaty-action, recorded-date or collection columns. `updated_at` remains the record version. Date provenance belongs to source evidence, including accepted field proofs, cited calendar/time-zone components and captured source content. Calendar generation has been removed.

The local and deployed schema through migration `20261007090000` has **four tables and 46 columns**. The migration drops `records.date_evidence`; dates retain their proofs in sources. Collector v88 and the matching frontend are deployed. Existing collector-proof permissions and trigger remain:

| Table | Columns | Purpose |
| --- | ---: | --- |
| `trackers` | 8 | Source configuration: name, URL, coverage, collector, cadence, proven-collector enabled flag, ID and seed identity. |
| `collection_runs` | 8 | Collection attempts, outcomes, coverage, statistics and nullable instrumented report, with warnings stored once. |
| `records` | 17 | Current finding, priority, last communication time, supported event times, identity and evidence timing. |
| `evidence` | 13 | Captured content and parsed facts, linked directly to a record and tracker, with source URL and observation times. |

A tracker defines where to collect; evidence stores what its returned URLs contained; a record holds the current finding supported by those captures. One record can have many captures. Shared captures are copied per record, avoiding a separate source-link table. Captures without a record remain stored. `current_evidence` selects the most recently seen capture for each record/URL, including returns to older content. Capture time, last-seen time and fact-change evidence time remain distinct.

**Enabled means a working, tested collector has been proven to receive and persist real source data for that exact tracker configuration.** Yes is not a schedule, heartbeat subscription, pause/resume setting, or guarantee of complete/current coverage. No means unimplemented, unconfigured, not yet proven, or proof invalidated by a source/configuration change. New trackers default to No. A completed Low finding or supported no-event result can prove collection; an HTTP 200, empty run, matching URL pattern, or passing fixture alone cannot.

The saved inventory has **17 reviewed Yes collectors out of 25**: four Bluesky author feeds, HUB Ocean, UN Treaty Collection, UN BBNJ/DOALOS, UN side events, IDDRI High Seas, DOSI BBNJ, GFW media centre, IUCN High Seas, Global Ocean Forum, OceanCare, Harvest Strategies, RISE UP and Blue Marine. The other **8 remain No**; [the complete audit](tasks.md#final-25-tracker-evidence-audit) records exact configurations, accepted proofs, pending counts and gaps. Scheduling remains separate and unimplemented. The per-tracker plan requires recorded examples, bounded live validation while disabled, a repeat check and manager review before explicit promotion. Changing the source URL/account or collector requires fresh proof; cadence changes alone do not. Do not turn a tracker on merely to test it.

Enabled writes belong to the private backend after review. Ordinary authenticated admins can still insert/edit tracker configuration, but must omit `enabled`; readers still cannot edit configuration. New rows default to No. The database resets Enabled to No whenever the URL or collector changes, including a backend update that also tries to retain/set Yes. An unchanged URL/collector or cadence-only edit retains proof. A later separate backend update can promote the reviewed configuration.

The browser reads current source metadata through `source_details`; direct raw-evidence access stays backend-only. The deployed SCOUT-17 backend below adds scoped reads of captures referenced by an instrumented run. `tracker_status` derives attempt/success/outcome/error from runs. These views store no additional data. Trackers have no cadence/configuration notes, cached status, timestamps or next-run field. There is no `memberships` table: backend-controlled Auth app metadata grants admin access to an otherwise eligible Workspace identity.

Source captures provide history. The migration removes deliveries and adds nullable `priority` and `last_communicated_at`; it neither infers priorities nor announces old records. A restricted source projection exposes the latest accepted relevance reason without raw captures. Records filter/order by priority or date, label null priority **Not yet assessed**, and distinguish **Unknown** from **Not applicable**. Notification selection uses the current assessment, dates and communication recency; there are no baseline, receipt, snapshot or replacement tables.

Cards, filters and digest windows use UTC; records store no time zone, creation time or material hash. New parser captures omit duplicate summaries, publication dates and schedule prose while retaining raw content. See [Database deployment](#database-deployment) for the coordinated migration and release status.

Import the tracker sheet once to seed the database, then let the app own subsequent tracker edits. Each tracker defines what to collect, its collection method, and its cadence. The current plan is daily Bluesky collection, mostly weekly website checks, and weekly discovery searches.

Use direct feeds, public APIs, and website collectors where possible. The sheet specifies Bluesky `getAuthorFeed` for account feeds and `searchPosts` for discovery; Tavily web discovery is a separate tracker. Follow results to supporting source pages, merge duplicate findings while retaining their sources, and update existing records when event details change. Preserve authoritative organizer corrections when older third-party reports are collected later. Verify treaty-status changes against the official record.

Derive each tracker's last attempt, last successful collection and latest completed outcome from collection runs. Failed collection or exhausted quotas must preserve existing records. Scheduling is not implemented.

### Workspace sign-in

The app uses Supabase's Google OAuth flow with PKCE and tab-scoped `sessionStorage` (`scout-auth`), so the verifier survives the Google redirect without saving a persistent cross-tab login. Sign-out immediately removes rendered data, prevents late access checks from restoring it, clears that tab's session and reloads the login screen. The `hd` sign-in parameter only helps select the account; it grants no access.

The hardened `scout.access_role()` function checks the current user's provider-owned `auth.identities` row: Google provider, Google token issuer, boolean verified email, and `custom_claims.hd = oceanagentics.com` are required. It returns `reader` automatically. Backend-controlled `auth.users.raw_app_meta_data.scout.admin = true` elevates an eligible identity to `admin`; migration `20261001170000` transfers existing admin memberships before removing that table. ## Continuous oldest-first collection (local implementation)

After deploying the function, enable Supabase Cron/pg_net and store the project URL as `scout_project_url` and the project's named default backend secret as `scout_collector_key` in Vault. The following SQL installs/replaces a **paused** trigger. It sends an empty body (`NULL`), matching the worker contract; its 30-second tick only wakes the loop, rather than imposing a tracker revisit interval. References: [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart), [pg_net POST implementation](https://github.com/supabase/pg_net/blob/master/sql/pg_net.sql).

```sql
begin;
do $$
begin
  if (select count(*) from vault.decrypted_secrets
      where name in ('scout_project_url','scout_collector_key') and decrypted_secret <> '') <> 2 then
    raise exception 'Scout URL and backend key must be configured in Vault';
  end if;
end $$;
select cron.schedule('scout-collect-next', '30 seconds', $job$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name='scout_project_url')
      || '/functions/v1/scout-collect-hsa?next=true',
    body := NULL::jsonb,
    headers := jsonb_build_object('apikey',
      (select decrypted_secret from vault.decrypted_secrets where name='scout_collector_key')),
    timeout_milliseconds := 110000
  );
$job$);
select cron.alter_job(job_id := jobid, active := false)
from cron.job where jobname='scout-collect-next';
commit;
```
