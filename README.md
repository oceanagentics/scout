# BBNJ Scout

Scout is Ocean Agentics' planned app for keeping up with BBNJ: treaty ratifications, NGO webinars, official DOALOS announcements, conferences, and side events. It will maintain a central database, surface useful changes in Slack, and make events easy to find with their supporting sources.

The deployed app, remote database, Workspace sign-in and manual collection are verified. HSA, DOSI, Global Fishing Watch, IDDRI and HUB Ocean have completed live assessments. The official UN Treaty Collection and DOALOS are enabled after manager review of their bounded live proof. The four-table system holds thirteen findings, including Mozambique's official accession, the November 5 BBNJ conference, the HUB Ocean AI/data webinar and the Ai2/GFW technical partnership. Remaining bounded coverage and pending assessments are recorded in [tasks.md](tasks.md). The minimal notifier has been previewed without a new Slack send; scheduling and other collectors remain deferred. The proof-of-concept target is **$0/month in recurring service fees**.

## Product brief

Scout should collect relevant events and official announcements into one maintained record, then help users answer questions such as:

> @scout does HSA have any webinars coming soon?

The planned experience includes:

- Updates on treaty ratifications and other official participant-status changes.
- BBNJ webinars, conferences, side events, and official DOALOS announcements.
- Daily Slack posts for new findings and material changes, plus a weekly roundup of upcoming events.
- Slack answers grounded in collected records, with supporting source links and visible coverage limits.
- A searchable, filterable web list with supported UTC event times and source links.
- A frontend list of all trackers showing collection status and last successful collection, including trackers that have never succeeded or are overdue.

The Letter mentions an optional weekly email digest; Features currently specifies a weekly Slack digest. The task plan proposes deferring email and a separate calendar view. Confirm that scope in SCOUT-01 before implementation.

## Records and collection

Records keep a title, type, organization, description of at most 280 characters, location, event/registration links, supported UTC start/end timestamps and status. Publication and collection timestamps belong to sources. Full text, date-only values and treaty details remain in captured source evidence; records no longer duplicate them in summary, date-only, publication, country, treaty-action, recorded-date or collection columns. `updated_at` remains the record version. Compact `date_evidence` references the schedule and zone captures used to establish a UTC instant; the component values stay in those captures. Calendar generation has been removed.

The schema through migration `20261002150000` has **four tables and 46 columns**; the latest migration protects collector proof with column permissions and a trigger, without adding columns:

| Table | Columns | Purpose |
| --- | ---: | --- |
| `trackers` | 8 | Source configuration: name, URL, coverage, collector, cadence, proven-collector enabled flag, ID and seed identity. |
| `collection_runs` | 7 | Collection attempts, outcomes, coverage and statistics, with warnings stored once. |
| `records` | 18 | Current finding, priority, last communication time, supported event times, identity and evidence references. |
| `evidence` | 13 | Captured content and parsed facts, linked directly to a record and tracker, with source URL and observation times. |

A tracker defines where to collect; evidence stores what its returned URLs contained; a record holds the current finding supported by those captures. One record can have many captures. Shared captures are copied per record, avoiding a separate source-link table. Captures without a record remain stored. `current_evidence` selects the most recently seen capture for each record/URL, including returns to older content. Capture time, last-seen time and fact-change evidence time remain distinct.

**Enabled means a working, tested collector has been proven to receive and persist real source data for that exact tracker configuration.** Yes is not a schedule, heartbeat subscription, pause/resume setting, or guarantee of complete/current coverage. No means unimplemented, unconfigured, not yet proven, or proof invalidated by a source/configuration change. New trackers default to No. A completed low-relevance/no-record decision can prove collection; an HTTP 200, empty run, matching URL pattern, or passing fixture alone cannot.

The reviewed hosted inventory has **eight proven collectors out of 25**: HSA, DOSI, GFW and IDDRI Bluesky feeds, HUB Ocean's calendar, UN Treaty Collection, UN BBNJ/DOALOS and UN meeting/side-event pages. Those eight are enabled; the other 17 remain No. DOSI/GFW partial coverage and the HSA supporting-source backlog remain visible in run outcomes and [tasks.md](tasks.md#scout-16--prove-and-enable-every-tracker). Scheduling remains separate and unimplemented. The per-tracker plan requires recorded examples, a bounded live validation while still disabled, a repeat check, and manager-reviewed evidence before explicit promotion to Yes. Changing the source URL/account or collector requires fresh proof; cadence changes alone do not. Do not turn a tracker on merely to test it.

Enabled writes belong to the private backend after review. Ordinary authenticated admins can still insert/edit tracker configuration, but must omit `enabled`; readers still cannot edit configuration. New rows default to No. The database resets Enabled to No whenever the URL or collector changes, including a backend update that also tries to retain/set Yes. An unchanged URL/collector or cadence-only edit retains proof. A later separate backend update can promote the reviewed configuration.

The browser reads current source metadata through `source_details`; raw evidence stays backend-only. `tracker_status` derives attempt/success/outcome/error from runs. These views store no additional data. Trackers have no cadence/configuration notes, cached status, timestamps or next-run field. There is no `memberships` table: backend-controlled Auth app metadata grants admin access to an otherwise eligible Workspace identity.

Source captures provide history. The migration removes deliveries and adds nullable `priority` and `last_communicated_at`; it neither infers priorities nor announces old records. A restricted source projection exposes the latest accepted relevance reason without raw captures. Records filter/order by priority or date, label null priority **Not yet assessed**, and distinguish **Unknown** from **Not applicable**. Notification selection uses the current assessment, dates and communication recency; there are no baseline, receipt, snapshot or replacement tables.

Cards, filters and digest windows use UTC; records store no time zone, creation time or material hash. New parser captures omit duplicate summaries, publication dates and schedule prose while retaining raw content. See [Database deployment](#database-deployment) for the coordinated migration and release status.

Import the tracker sheet once to seed the database, then let the app own subsequent tracker edits. Each tracker defines what to collect, its collection method, and its cadence. The current plan is daily Bluesky collection, mostly weekly website checks, and weekly discovery searches.

Use direct feeds, public APIs, and website collectors where possible. The sheet specifies Bluesky `getAuthorFeed` for account feeds and `searchPosts` for discovery; Tavily web discovery is a separate tracker. Follow results to supporting source pages, merge duplicate findings while retaining their sources, and update existing records when event details change. Preserve authoritative organizer corrections when older third-party reports are collected later. Verify treaty-status changes against the official record.

Derive each tracker's last attempt, last successful collection and latest completed outcome from collection runs. Failed collection or exhausted quotas must preserve existing records. Scheduling is not implemented.

### Workspace sign-in

The app uses Supabase's Google OAuth flow with PKCE and tab-scoped `sessionStorage` (`scout-auth`), so the verifier survives the Google redirect without saving a persistent cross-tab login. Sign-out immediately removes rendered data, prevents late access checks from restoring it, clears that tab's session and reloads the login screen. The `hd` sign-in parameter only helps select the account; it grants no access.

The hardened `scout.access_role()` function checks the current user's provider-owned `auth.identities` row: Google provider, Google token issuer, boolean verified email, and `custom_claims.hd = oceanagentics.com` are required. It returns `reader` automatically. Backend-controlled `auth.users.raw_app_meta_data.scout.admin = true` elevates an eligible identity to `admin`; migration `20261001170000` transfers existing admin memberships before removing that table. No admin was provisioned. Read and tracker-write policies enforce access independently of the UI. Clients cannot modify provider identities or app metadata, or read raw evidence and delivery state. User-editable `raw_user_meta_data` is not trusted. This matches the verified GoTrue `v2.197.0` [Google token verification](https://github.com/supabase/auth/blob/v2.197.0/internal/api/provider/google.go), [hosted-domain extraction](https://github.com/supabase/auth/blob/v2.197.0/internal/api/provider/oidc.go) and [separate user-metadata update](https://github.com/supabase/auth/blob/v2.197.0/internal/models/user.go); Google's [OpenID guidance](https://developers.google.com/identity/openid-connect/openid-connect) distinguishes the signed `hd` claim from the request hint.

Feed limits remain two pages of 25 posts, two supporting links per post, six pages, three redirects, 24 requests, 512 KiB/response and 12 seconds/request within 120 seconds locally or 100 seconds hosted. The explicit User-Agent and HTTPS/socket-level DNS checks remain. Technical/official links are followed even when the parent post is unchanged. PDFs, quoted posts and unresolved multi-event pages remain explicit coverage limits. Tavily is unused.

The `hsa-v4` gate compares normalized text, author, links and structured facts before model work, retaining hashes per field and changed-field names. Whitespace, tracking parameters and page scripts do not create captures. A→B→A reuses A's capture but reassesses the transition. Full captures remain reconstructable; unchanged content produces no new evidence or record versions. Pending work resumes independently of fetch changes and precedes uncertainty. A fully evaluated uncertain decision retains its reason/pending count but reuses its assessment when source, coverage, candidate facts and supporting evidence are unchanged. The fingerprint lives in existing assessment metadata; changed context or explicitly marking the evidence pending allows reassessment. A race-guard deferral is not cached as evaluated uncertainty. Assessment-version changes do not silently reprocess completed sources; explicitly mark selected current evidence pending before a deliberate reprocessing run.

Assessment uses bounded useful text (including changed text beyond a long HTML head), deterministic extraction, tracker coverage and up to three candidate records. Requests batch at most two independent sources, splitting when the input bound requires it. Sources are data, not instructions. Every applicable field must be present with a supported value or explicit null; blank/omitted keys, unsupported dates/URLs, invalid identity choices and unverified treaty changes are rejected. A first-batch possible duplicate remains pending for a refreshed shortlist. That guard checks candidates absent from the model's original shortlist, retaining stable-source/exact-event protections; shared topic/organizer alone does not override a reviewed distinct-finding decision. Sessions/editions sharing a URL stay distinct. Unknown facts preserve established facts; explicit supported withdrawals pass authority checks before clearing them. Relevance is accepted separately from fact authority: weaker evidence can change priority without overwriting an authoritative cancellation or date.

Priorities follow the approved rubric: technical ChM/implementation work and verified important official changes high; other substantive BBNJ events/announcements normal; generic advocacy/incidental content low.
