# Scout architecture

Scout saves BBNJ events, announcements and treaty developments in flat findings shared by the website, Slack and calendar. Collection wakes every six minutes and checks one due tracker. The company timezone is America/New_York; stored instants remain UTC and published dates retain their precision. Deployment instructions are in [README](../README.md#supabase-deployment).

## Volunteer review

The website opens on Review for verified Ocean Agentics accounts. [review.js](../website/review.js) shows one unreviewed finding at a time, its description, source links and model ranking, with Low/Normal/High buttons and required notes explaining the ranking. Save stays disabled until the reviewer selects a ranking, enters nonblank notes and opens a source link for that card. Hovering or focusing its disabled wrapper shows a tooltip explaining these requirements. Source buttons lead their row and show opened/unopened states. The click state is browser-only and resets for each card; it is not proof that the source was read. The compact layout keeps source links and controls visible within the viewport; long descriptions scroll inside the card. Desktop places the finding beside the form, and mobile stacks them. [dashboard.js](../website/dashboard.js) owns navigation to Review, Records, Trackers and Calendar; all views share the compact nav with consistent padding and link weights. Direct record links still open Records. Records and tracker inventory load only when those views are first opened. Calendar uses Google's exact shareable link, including its unpadded cid, for the existing Scout Google calendar. Its instructions pair full-header and left-sidebar Google Calendar screenshots from website/public/calendar with control close-ups. CSS markers show the account icon, calendar-list sections and Scout checkbox; a real already-added notification explains that state. These static UI crops exclude personal events, names and email addresses; they do not request an iCal feed link or change sharing permissions.

`scout.review_queue()` returns the next finding and the signed-in reviewer's count. `scout.submit_review(uuid,timestamptz,text,text)` requires nonblank notes, verifies the exact displayed revision, saves feedback and returns the next card and committed count in the same transaction. Previously saved feedback is preserved. Lost-response retries and concurrent submissions cannot create a second review for the same reviewer/finding. A changed or deleted finding requires reloading before submission. Findings already reviewed are not reassigned when edited.

`scout.finding_reviews` stores one row per reviewer/finding: model score at submission, independent Low/Normal/High reviewer category, notes and submission time. Feedback never overwrites model findings or changes collection, Slack or calendars. Reviewers can read their own feedback; Scout admins can read all feedback. Writes go through the authenticated RPC; neither anonymous nor unverified accounts can access the queue or submit. There are no model calls, scheduled work or separate score counters. Personal counts come from saved reviews. A small count animation follows confirmed saves; each crossed multiple of 12 opens a full-screen celebration, with a static version for reduced-motion preferences.

The same table holds a separate `origin='slack'` class of reference cases for background Triage and ranking analysis. They are not surfaced in the review UI. Existing rows retain `origin='reviewer'` and their reviewer/finding uniqueness; a UUID identifies each row. Slack rows retain a short useful finding description, `source_url`, `slack_url`, `slack_author_id`, `slack_author_name`, `slack_posted_at`, expected `priority`, optional observed `model_priority` or `model_score` and concise notes. They have no reviewer or production-record association, so missed findings can be recorded without creating production findings or attributing a review to the poster. A unique `(slack_url,source_url)` key makes repeated scans write nothing while preserving independent posts of the same source. The existing read policy keeps these cases accessible only to backend/admin analysis; backend access alone can insert them. Volunteer feedback stays private and counts/queues remain unchanged. No browser functions or API calls are added.

The same table accepts `origin='slack_feedback'` for human comments and reactions on Scout posts in `#scout` and Danny's existing Scout DM. Triage writes these through backend access. Existing columns hold a verified `record_id` when available, the finding description, feedback author's Slack ID/name, message permalink/time and concise notes distinguishing comments from exact emoji reactions. For a reaction, `slack_posted_at` is the target message's time; Slack history does not establish when the reaction was added. `reviewed_at` records capture or a substantive feedback change. The model score is captured once, identifying a current saved score when a posting-time score is unavailable. `priority` may be null for Slack feedback; unexplained emojis are not categorical votes. `reviewer_id` and `source_url` stay null: finding sources remain on the associated record, while public-link references keep their existing source URL and uniqueness. A partial unique index on `(slack_url,slack_author_id)` gives each message/person one current feedback account; changed comments/reactions update its notes and explicit priority, while identical scans make no writes. Reaction removals are recorded as withdrawn feedback, not a new vote. The existing RLS policy makes these rows admin-only, and their null reviewer IDs keep them outside volunteer counts and queue exclusions. No RPC or browser changes are needed.

The existing daily local Triage automation checks new human postings in public OA Slack channels and inserts new relevant references into `finding_reviews`; Ranking Feedback also saves the authorized Scout DM/channel feedback above. Bots and Scout's own messages are not human feedback. Successfully completed scans in the Triage chat establish their independent coverage; incomplete scans never advance it and no checkpoint file or scan history is added. Source bodies and Slack messages are read in memory and discarded after retaining the compact feedback/reference cases. Human sharing is stronger evidence for rubric assessment than a volunteer rating alone, with Aaron’s webinar an expected High reference. No numerical weighting algorithm or automatic rubric/score changes are introduced. Reuse the existing batched database and Slack reads; add one batched upsert for new or changed feedback and a readback of affected rows. There are zero separate Scout model calls and no finding, notification, calendar or job writes.

## Shared item ingestion

```mermaid
flowchart TD
  request[Scheduled or explicit check] --> intake[reader/intake.js: claim and deadlines]
  intake --> ingestion[reader/ingestion.js: sequential item consumption]
  ingestion --> adapters[reader/sources: Bluesky, RSS, News search, webpage discovery, CBD]
  adapters --> http[reader/url.js and freshness.js]
  adapters --> items[Individual publication URLs and available material]
  items --> investigate[reader/investigate.js]
  investigate -->|read_url| http
  investigate -->|search_findings| findings[reader/findings.js]
  findings --> records[(scout.records)]
  ingestion --> progress[reader/progress.js]
  progress --> state[(trackers and source_items)]
  records --> outputs[Website, Slack and calendar]
```

The authenticated [hosted reader](../supabase/functions/scout-reader/index.ts) reserves one database connection and calls intake. Intake atomically claims a tracker with a 120-second lease, then invokes the shared ingestion service. Source/model work happens outside database transactions. An explicit tracker ID can retry a source that stopped after three unsuccessful attempts, without stealing a live lease.

[Source adapters](../reader/sources/index.js) enumerate publications; they do not decide relevance or match findings. The tracker's collector setting is explicit: web_page (Page), web_index (Index) or bluesky_feed. Page investigates the complete configured page as one item, retaining its public URL; investigation can still follow relevant links. Index enumerates publications using RSS/Atom or webpage discovery. Bluesky retains native author-feed pagination and consumed-through timestamp groups. RSS/Atom uses a pinned XML parser, publisher GUID/ID or observed permalink, and a digest of stable entry fields. Webpage discovery uses a separate model schema to identify observed entry URLs and available summaries. Within the same bounded model attempt it can read linked publication collections and return their individual article/PDF URLs; returned URLs must be observed in the supplied page or a page read during discovery. It excludes the index itself and its alternate exports. Invalid links are excluded and counted; valid items can save while a partial discovery remains unacknowledged. Native PDF/image resources remain singleton items. CBD uses its existing public article API mapping while retaining the public page URL.

An item carries key, public url, optional published_at/version, source_kind and invocation-local prepared content. Native posts require published_at for their original publication time; their separate at field tracks feed activity, including reposts. Original publication timestamps are not persisted; activity timestamps supply the existing tracker checkpoint. Its public URL is trusted caller context: it is never taken from the model's returned finding fields. A feed endpoint, CBD API endpoint or tracker homepage cannot silently replace that URL. A homepage is a finding URL only when the homepage itself is the investigated item.

[Search discovery](../reader/sources/search.js) runs one backend-managed `search_query` per Index tracker at `https://api.tavily.com/search`. The services gateway supplies Tavily's credential and a 20-second bound clipped to the collection deadline. The backend-only `search_topic` selects `news` (default) or `general`; LinkedIn uses `general`. Basic search requests up to 20 results without answers, automatic parameter selection or automatic extraction. Code validates and deduplicates URLs without a discovery model and returns ordinary unversioned web items without snippets. The sorted distinct URL set is hashed by the existing content-freshness helper and committed to `discovery_fingerprint`; discovery HTTP metadata stays null. An unchanged result set still registers its URLs for individual resource freshness checks. `retainMissing:true` preserves completed receipts when URLs disappear. Pending work resumes before another search. Existing finite retries apply to each tracker; there is no search-provider fallback or cross-tracker receipt cache. Invocation-only `source.search` counters report requests, returned results and provider-declared credits. Provider replies remain in memory.

The [ingestion service](../reader/ingestion.js) applies native post age eligibility immediately after discovery, before registration or investigation. Intake supplies oldest_date, one calendar month before the check's New York date. Original publication days before that cutoff are excluded without model calls or per-post SQL writes. Web/RSS publication dates are publisher hints and cannot discard new or changed items by themselves; unchanged versions and resource freshness retain their existing skips. Investigation still filters confirmed-old findings by their finding dates before saving.

The ingestion service durably registers discovered non-native item keys, URLs and versions before investigation. Items run sequentially through one investigation and commit independently. The finding writes and consumed progress share one short transaction with lease/URL validation. Irrelevant and explicit identity-skip outcomes still consume the item. An unavailable/invalid child URL without supplied material, unreadable or incomplete item output, or an attempted item's timeout commits a skip and continues to later items while the work deadline permits. Supplied feed/discovery material can still be investigated after a failed detail read. Database/save/lease failures and provider-wide failures remain deferred; unattempted items remain pending. Earlier committed items survive a later timeout. Pending items resume before rediscovery, using their saved URLs; no source body or model conversation is stored.

Non-native item rows retain one current last_error reason beside their existing URL and consumed_at time, including failed detail reads handled with supplied material. Skips set pending=false without acknowledging a successful resource read or changing its previous timestamp/fingerprint. A completed traversal can therefore include skipped items. Changed URLs/versions clear obsolete warnings, and successful processing clears an item's warning. An unchanged index does not repeat a skipped item; changed unversioned listings can requeue it unless explicitly ignored. The daily Scout triage in the existing local chat reports new/changed item warnings and recoveries with the tracker, URL and reason; unchanged warnings remain quiet. Ignored items are excluded from actionable warnings; dismissal is not successful retrieval or recovery. No new notification job, outbox or failure history is stored.

Bluesky starts with a null checkpoint and reads eligible posts oldest first across bounded attempts, excluding pinned posts and deferring posts newer than the invocation start. Each investigation receives the current post, its own attachments and optional repost metadata, excluding the feed's embedded parent/root bodies so their announcements cannot be attributed to a later reply. The current post's reply references remain available for contextual reads. Pagination stops when feed activity crosses the age boundary or committed checkpoint. A recent repost of an expired original does not stop pagination; shared ingestion excludes it using the original publication time. Posts sharing an activity timestamp commit atomically. Later posts in that group see earlier proposed findings in memory, including proposed IDs and source URLs. A failed group remains unconsumed. After a complete scan, including one with no eligible posts, its native checkpoint advances to the check start. The age cutoff is never seeded as progress. Unchanged feeds make no model calls. Date-only native progress can miss late/backdated posts behind its cutoff; it does not introduce a second receipt table for already consumed history.

## HTTP and freshness

[reader/url.js](../reader/url.js) owns public-address checks, redirect validation, a 15-second HTTP bound and invocation-local response caching. HTML preparation retains ordered text, tables, absolute links, images and published structured data. JSON remains structured; XML is available to the RSS adapter. Native PDF/image checks cancel response bodies and provide URL descriptors to the model adapters.

`isBlockedPage` recognizes known bot challenges and the existing empty Angular shell. After public-address and redirect validation, a `cf-mitigated: challenge` response, recognized blocked HTML, or a connection reset while fetching invokes the scraping gateway. Reset detection accepts `ECONNRESET` on the error/cause or the connection-reset message emitted by hosted fetch. It applies only after the current redirect target passes validation and before the HTTP or collection deadline expires. Working/unchanged reads, native PDF/images, ordinary HTTP errors, other transport failures and invalid/private targets retain their direct paths. Direct HTTP has a 15-second deadline; extraction receives the caller's collection signal instead of inheriting that HTTP timer. Each gateway attempt combines a fresh 20-second client timer with the caller's signal, and each provider is asked to use a 15-second server timeout. A provider timeout permits failover; expiration of the collection deadline stops the chain. Intake combines caller-supplied cancellation with its remaining 100-second collection deadline. All reads retain the invocation cache. A shared challenge detector rejects challenge text returned by extraction services too.

[reader/services/gateway.js](../reader/services/gateway.js) is constructed once by intake. Its scraping path tries anonymous Jina browser rendering, keyed Tavily Advanced Extract, then keyed Firecrawl. Missing keys skip the corresponding scraping service. Provider adapters prepare requests, validate upstream status/results and return article content; HTTP 200 alone is not success. Quota/authentication/rate-limit/server errors exclude that scraping service for the remainder of the check, including subsequent URLs. A page-specific failure only falls through for that page. A new check starts with no excluded services, allowing provider renewals to recover automatically. The gateway also exposes keyed Tavily News search. There is no persistent quota state, credit ledger, polling job or UI control. Pending concurrent requests can encounter a quota before another request reports it.

Fallback content uses `text/markdown` with the validated public source URL, never a service endpoint. Its `request_url`, `checked_at` and fingerprint are null and `unchanged` is false: provider caches and API metadata cannot acknowledge a successful HTTP freshness check of the source. Existing committed HTTP read metadata is preserved by item consumption; index discovery without source freshness cannot skip investigation. Bodies and provider replies stay in memory. Jina requests fresh browser content with DNT; Firecrawl requests fresh content without storing it in its index/cache. Keys enter through the hosted/local entrypoints. Invocation-only numeric `source.scraping` counts track provider attempts; existing HTTP metrics include provider requests and response bytes. Routing adds zero SQL/model calls and at most three extraction attempts per blocked URL; usable recovered pages may require additional normal investigations. Actual hosted allowance use and end-to-end model/SQL costs must be measured before unattended operation.

Failed reads return the validated request URL, failure stage (including scraping), HTTP status when received, and bounded sanitized transport error name/code/message in the invocation's existing diagnostics. Root discovery failures and failed detail reads handled with supplied material retain these details. Bodies and headers are not included, and no diagnostic traffic or new history is persisted. Existing failure reasons, tracker retries and invocation timeouts remain unchanged.

The unchanged checker remains [reader/freshness.js](../reader/freshness.js). It sends If-Modified-Since after a successfully processed read and accepts 304 or an older/equal Last-Modified on a successful 200. When HTTP cannot establish freshness, the URL reader prepares the body and the checker compares its SHA-256 fingerprint, including the media type. HTML hashes cover the readable text, links, images and structured data supplied to the model; JSON/XML/text use their prepared content. Native PDF/image descriptors remain HTTP-only because their bytes are not read here. There is no additional HEAD request or stored ETag.

The index is checked before discovery. Each candidate article is checked before starting its model investigation; a confirmed unchanged article consumes pending progress without a model call. Pending work remains resumable even if the index is unchanged. Invocation-local caching retains prepared bodies, so each caller compares against its own committed fingerprint; a conditional response without a body cannot establish freshness for another caller.

Freshness metadata belongs to the exact fetched resource, including query parameters and redirect destinations. A listing checkpoint, feed entry consumption time or different API endpoint never establishes article freshness. Store the conservative request-start timestamp and candidate fingerprint only with successful discovery or item processing. Keep only the latest successfully processed fingerprint, overwriting it in the existing progress transaction; there is no history or stored body. Failed investigations/saves and incomplete discovery cannot acknowledge their reads. HTTP-confirmed unchanged reads preserve the prior hash. Supporting URLs have no inherited checkpoint. New source adapters use this same gate rather than adding their own checker. Changes only in linked resources remain undetected when their parent is confirmed unchanged.

## Compact progress state

scout.trackers retains name/URL/configuration, backend-only search_query and search_topic, retire_on, last_checked_at, last_successful_check, last_error, failure_count, lease_id and lease_until. The unique source index includes URL, collector and the query (empty for ordinary trackers), allowing independent queries at the same endpoint. Its discovery_request_url, discovery_checked_at and discovery_fingerprint acknowledge listing discovery before pending articles finish. Search fingerprints acknowledge URL membership only, with no HTTP checkpoint. last_successful_check is the native Bluesky watermark or the latest fully completed source check, not an arbitrary article timestamp.

The backend-only scout.source_items table contains tracker_id + item_key as its primary key, url, observed_version, consumed_version, pending, consumed_at, request_url, request_checked_at, request_fingerprint, last_error and ignored. It stores current receipts and pending addresses, never summaries, documents, prompts, responses or candidate snapshots. Completed items absent from a successful fresh listing are pruned except for retained search receipts; pending and ignored items are retained. Explicit backend dismissal sets ignored=true and pending=false while the tracker is idle, preserving error and read metadata. A database constraint prevents ignored items from being pending. Registration neither updates nor prunes ignored rows, so changed listings and disappearance/reappearance cannot retry them. Ignore decisions belong to the existing tracker/item key, not a global URL blocklist; new rows default to ignored=false. RSS unchanged versions do not repeat investigation; webpage entries with no reliable revision use article freshness. This adds one boolean per item, with no extra recurring queries, model calls or jobs. This is one compact current-state table, not a queue/history service or a new scheduled job.

New trackers have no checkpoint. Changing a URL or search query clears ordinary source state and disables automatic checking until backend enablement, while preserving findings and ignored item receipts. Changing Page/Index clears ordinary source progress and any active lease, preserving the enabled state, findings and ignored item receipts. Deleting the tracker removes all of its item rows. Tracker configuration is managed agentically; the website's Trackers table displays the current setting without editing controls. Retirement applies to scheduled, explicit and diagnostic checks. Three attempts without progress stop automatic retries; successful item commits reset the failure streak. Cadence uses completed New York days, with pending/incomplete work eligible on subsequent six-minute wakes. Browser users cannot write operational fields, read leases or access source_items.

## Investigation, duplicate search and saving

[reader/investigate.js](../reader/investigate.js) supplies one item, the common finding instructions, dates and two tools: read_url and search_findings. The model assesses relevance, reads further as needed and searches saved records before creating or updating. Searches combine ORed text phrases (each phrase matches all its words) and exact source URLs. They cover descriptions, organizations and details without restrictive type/date filters or result-count caps, and return full candidates with exact PostgreSQL revision strings.

[reader/ingestion.js](../reader/ingestion.js) first investigates each source item with GPT-6 Luna at low effort. An accepted create/update score above zero promotes the whole source URL to a second full investigation with GPT-6.1 Terra at none effort and temperature zero. Both passes use the exact same instruction, schema and compiled rubric. Terra owns its final facts, scores, matching IDs and create/update/skip decisions; Luna's preliminary positive decisions are not saved. Zero/null-only sources bypass Terra. Mixed sources retain Luna's zero/null findings as uncommitted entries and expose them through the existing pending-candidate mechanism so Terra can update them. Prior tied-post results and evidence remain available until the group's existing transaction commits.

The invocation-local evidence map retains original item content, full prepared pages and native PDF/image descriptors. Terra receives available evidence once, with PDFs/images as actual native input parts, plus provider search references that remain references rather than claimed page bodies. The existing read/search tools can obtain missing evidence. Fully supplied source URLs qualify as read supporting sources; references alone do not. No evidence is clipped to a Scout token cap or retained in production. A Terra transport, validation, timeout or context failure defers the current item/group as terra_failed, retaining the sanitized underlying cause. A result whose native-input recovery dropped a supplied file also defers. Neither provisional findings nor failed-item progress commits; earlier successful groups remain committed. There is no Luna-only fallback after a failed second pass.

The model is instructed to include a responsible organization name alone alongside specific topic queries and broaden unsuccessful searches. Creating a finding requires a duplicate search; empty results are valid and the backend does not require a particular query wording. Matching is a model decision after retrieval; there is no separate matcher model call or description/80-percent-word/sole-source heuristic fallback.

The investigation instructions provide OA's mission, research and original-date requirements, active research of both event endpoints, and the shared numeric ranking policy compiled from [shared/rankings.md](../shared/rankings.md). The result has complete/unreadable status and explicit create, update or skip decisions. Updates require a searched candidate ID with full proposed fields even when facts are unchanged. Revision and modification metadata remain in backend search snapshots, outside the model-facing candidates and response. The backend builds sources from the trusted item URL plus actually read supporting URLs, saves a new item URL through the normal update path and makes no finding write when the merged record is identical. Skip means a completed decision not to save an irrelevant or confirmed-old development, with a free-text reason; low-scored findings remain eligible. A supplied replacement date is accepted even when it conflicts with the saved date; the conflict does not discard the update or its source URL.

[reader/findings.js](../reader/findings.js) normalizes supported fields and applies explicit decisions under the existing transaction advisory lock. It repeats actual candidate searches immediately before writing and rejects a changed search set or revision, including a competing create. Identical merged findings make no record writes. Incoming final scores replace saved scores even when facts are unchanged or only a source is added; zero and unassessed null remain authoritative. Supplied dates replace saved dates at the incoming precision, including corrections from an exact day to a month or year. Missing optional facts preserve saved values; clock/end validity checks and source merging remain in place. A saved change appends one modified timestamp. The only in-group create coalescing is exact normalized field equality; it retains every item's source URL.

## Finding fields and URLs

| Column | Value |
| --- | --- |
| id | UUID |
| description | Short organization-led description, at most 280 Unicode characters |
| details | Nullable scalar text, at most 4,096 Unicode characters; searchable identifying facts, no model traffic or proof trail |
| type | event, announcement, or null |
| score | Integer 0–100, or null when unassessed |
| organizations | Organization name strings |
| date, enddate | YYYY-MM-DD, YYYY-MM, YYYY, or null |
| starttime, endtime, timezone | Published scalar strings or null |
| sources | JSON array of objects with url, role (finding, supporting or unclassified), and optional brief publisher name |
| modified | Creation and saved-change UTC timestamps |

The one-time source conversion preserves every old URL as unclassified, along with IDs and timestamps; it does not fabricate a primary link. Merge sources by normalized URL, applying the incoming explicit role so a read supporting page can correct an earlier finding label. The current item URL always remains a finding source. Investigation supplies its publisher's brief organization name as source_name, saved as sources[].name; a later unnamed read preserves that name. Several publications can support one finding and an article can produce several findings. Slack chooses the first evidenced finding URL and labels it with its saved publisher name, such as Bloomberg. Existing unnamed sources retain Read more; legacy records without an evidenced finding URL retain their description and omit the link. The website labels source roles and exposes details; calendar descriptions retain all URLs.

Treaty developments are announcements. The field-removal migration preserves their IDs, saved dates, sources and review feedback, and moves saved submission deadlines into searchable details within the details limit. Converted records retain prior modified timestamps and append one saved-change timestamp. A details overflow aborts the migration rather than losing a fact.

Field meanings appear once in the investigation prompt; the lean response schema defines structure, nullability, enums and character ceilings. The normalizer clips generated descriptions and details by Unicode characters before comparisons and writes. Database character checks enforce the same ceilings. Existing overlong descriptions are clipped to 280 characters and the description check is fully validated. Details can occupy up to 16 KiB of UTF-8 text. Clipping adds no model calls or per-item SQL and may discard trailing qualifiers, so identifying details come first.

The investigation input supplies the existing one-calendar-month backend cutoff as `oldest_date`; the prompt and backend use that same boundary and applies to normalized facts of every type. Unknown/future dates remain eligible; partial dates are excluded only if their latest possible day is before the cutoff. Malformed optional dates, ends or non-text details are dropped with numeric field counts without losing useful fields. Missing optional facts retain saved values; supplied dates retain their incoming precision. Existing findings are not deleted by this capture rule. The findings RPC includes details in text search, filters dates using date alone, and retains its workspace access and pagination.

The numeric migration maps existing Low/Normal/High findings to provisional scores of 25/60/85 without changing their facts, revisions or Slack receipts. Historical volunteer and Slack category feedback remains unchanged; volunteer reviews store the observed `model_score` and the human category in `priority`. The unused numeric human-score column was removed after verifying no numeric human votes existed; the migration locks the table and refuses to remove any saved vote. Human categories and notes are used for offline calibration; collection does not load reviews or Slack reference cases into model requests. Records support minimum-score and unassessed filters with descending score/date/ID pagination, placing null scores last. `PUBLICATION_SCORE` in shared/records.js owns the publication threshold, initially 75. The editable Markdown is compiled by `npm run build:rankings` into a committed JavaScript string; tests check exact equality. No runtime Markdown loading, dependencies or deployment flags are added. There is no bulk historical or scheduled reranking pass.

## Models, deadlines and cost

[reader/models](../reader/models/) owns provider protocol, JSON schema, tool continuations and finite fallback. Workflow-specific schemas/validation live with discovery and investigation. The reader explicitly requests OpenAI models for both investigation passes; the gateway needs no task identity. Explicit diagnostic provider selection disables fallback. Gemini and OpenAI support custom read/search continuations while preserving their native call IDs/signatures. OpenAI uses store:false. Failed native file inputs get the existing single recovery continuation and are not resubmitted; ingestion refuses a Terra result with dropped native inputs.

[gateway.js](../reader/models/gateway.js) exports `trackerModel`, used by the hosted reader and local tracker diagnostics. The hosted reader forwards the requested model through `modelFor`; HTML index discovery in `webItems` uses the existing Luna default. RSS/Bluesky enumeration, persistence, Slack delivery and calendar publishing do not call models. The gateway retains its standalone Gemini post default and eligible OpenAI fallback, but investigation explicitly selects Luna followed conditionally by Terra. Callers can explicitly select `model:'gpt-5.6-terra'` (low reasoning), `model:'gpt-6.1-sol'` (xhigh reasoning), `model:'gpt-6-luna'` (low reasoning), or `model:'gpt-6.1-terra'` (none reasoning, temperature zero). Explicit model selection uses OpenAI and disables fallback; it is incompatible with `provider:'gemini'`. The fixed OpenAI model/reasoning selections live in [openai.js](../reader/models/openai.js), sharing the existing Responses API adapter. The local diagnostic CLI exposes the same selection through `--model`, overriding both passes rather than changing the production route. Complimentary-token enrollment belongs to OpenAI's account settings; the gateway uses the standard service tier and stores no quota tracker.

Initial retrieval, both investigations and every model continuation share a 100-second invocation deadline; Gemini diagnostics are additionally bounded to 45 seconds per attempt. Commit transactions have an invocation-relative 110-second cutoff, statements clipped to remaining time, and post-commit callbacks a 115-second cutoff. The lease and scheduled caller remain 120 seconds, and the manual caller 125. A first-pass non-native item timeout uses the commit allowance to record its skip; a second-pass failure leaves the item pending. Exhausting the work budget before starting an item also leaves it pending. Responses include partial committed counts and skipped URL/reason diagnostics. Notifications/calendar callbacks do not replay ingestion; daily calendar reconciliation repairs interrupted publication.

Numeric invocation diagnostics measure provider requests/tokens, HTTP requests/bytes, SQL statements/mutations/bytes and elapsed work. No content, parameters, model usage ledger, uncertain-charge reservation or operation report is persisted. The service adds no jobs, per-investigation finding/tool caps or paid infrastructure. Cost scales with changed discovery pages, pending/changed articles, tool continuations, candidate searches and actual record changes. Existing account allowances and provider limits apply; estimates and acceptance cases are described in the [shared ingestion design](shared-ingestion-architecture.md).

For N investigated items and P promising URLs, the workflow makes N Luna attempts plus P Terra attempts, including separate tool continuations. Terra repeats candidate searches and their existing commit-time replay. Full-evidence input, cache writes/reads, search and all positive updates determine cost; saved-record counts are not call counts. The frozen Rio experiment is not a measurement of this production loop. Live score quality, full-pipeline latency and fit within the $50/month project budget remain unverified; measure those locally against actual account usage before deployment.

## Other components

- [website/](../website/) displays findings and tracker state. Firebase hosts the static interface; Supabase Auth and RLS protect data. Verified Ocean Agentics Google identities retain reader access and backend-granted admin roles.
- The Jobs tab is available to all verified Scout users and reads `scout.jobs()` through the existing authenticated Supabase HTTP API. It displays separate Supabase functions and cron tables. The function checks `access_role()`, reads the private Vault credential `scout_functions_read_key`, and uses the `http` extension to query the project's Management API inventory with one GET under the extension's default five-second timeout. Supabase restricts custom HTTP timeout settings, so the RPC uses that finite built-in bound. Only deployed `scout-` function names, status, version and update time are returned; unrelated functions and deployment paths are omitted. No function registry or trigger descriptions are maintained: Supabase's inventory does not expose callers. Cron data comes directly from every current `cron.job` and its latest `cron.job_run_details` row, excluding commands and credentials. The old `scout.cron()` RPC is removed. New functions and schedules appear automatically. The schedule is grouped under Schedule (UTC) with compact min, hor, day, mon and dow columns. The page refreshes on opening, manually and once per minute while visible, with timestamps in New York.
